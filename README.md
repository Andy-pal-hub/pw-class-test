# Perfect World — Путь героя · пилот v0.4

Интерактивный тест выбора одного из 17 классов, построенный на Google-матрице проекта. 4 исходных вопроса + адаптивные уточнения (до 10 классовых вопросов), проверка устойчивости и противоречий. Дополнительные шуточные вопросы — **демонстрационные**, пока не утверждён банк из 30 вопросов.

## Что входит

- `index.html` — основной сайт (HTML/CSS/JS без npm-библиотек или удалённых шрифтов).
- `config.js` — **публичная** конфигурация адреса приёмника, без паролей.
- `telemetry-client.js` — отправка данных и локальная очередь, если приёмник недоступен.
- `data/runs.json` — завершённые прохождения: обезличенный `session_id`, ответы и итоговый рейтинг.
- `data/feedback.json` — отзывы по конкретным вопросам, идентифицированные `question_id` (например, `Q01`, `U16`).
- `worker/worker.js`, `worker/wrangler.toml` — отдельный серверный приёмник Cloudflare Workers, который безопасно записывает в JSON-файлы на GitHub через секрет.
- `tools/analyze.py` — сводка из накопленных JSON-файлов.

## Важное ограничение GitHub Pages

GitHub Pages — статический хостинг и сам по себе **не умеет принимать POST-запросы и сохранять их в файлы репозитория**. Для приёма нужен Worker с отдельным секретом. **Не записывайте GitHub PAT в `index.html`, `config.js` и другой клиентский код.**

На момент подготовки пакета публичный адрес **не подтверждён и приёмник не запущен**. До настройки Worker отзывы попадают только в локальную очередь браузера, откуда их можно выгрузить кнопкой «Экспорт очереди отзывов · JSON». Автоматического общего сбора без Worker нет.

## Этап 1. Создать GitHub Pages

1. Используйте созданный репозиторий **`Andy-pal-hub/pw-class-test`**. Он должен быть публичным для обычного бесплатного GitHub Pages. Если он приватный, проверьте доступность Pages на вашем плане.
2. Скопируйте содержимое этой папки в корень репозитория. Не загружайте чужие личные данные, PAT и `.dev.vars`.
3. Откройте `Settings → Pages → Build and deployment → Deploy from a branch` и выберите `main / (root)`, затем `Save`.
4. GitHub Pages покажет ссылку на опубликованный сайт в `Settings → Pages` после успешной сборки. Для указанного репозитория адрес будет *предположительно* `https://andy-pal-hub.github.io/pw-class-test/`, **не считать адрес действующим, пока GitHub не подтвердит публикацию**.

## Этап 2. Подключить автоматический сбор статистики

Для пилота из двух-трёх пользователей — простая схема «браузер → Cloudflare Worker → GitHub JSON». Отзывы и прохождения будут видны в открытом репозитории, поэтому на сайте показано предупреждение: нельзя указывать имена, контакты или другую личную информацию.

1. В GitHub откройте `Settings → Developer settings → Personal access tokens → Fine-grained tokens`. Создайте токен **только для репозитория `pw-class-test`**, разрешение **Contents: Read and write**, с ограниченным сроком жизни. Токен не пересылайте в чаты и не вставляйте в клиентские файлы.
2. Зарегистрируйте/откройте Cloudflare Workers, установите Node.js на своём ПК. В консоли откройте папку `worker/` из этого проекта.
3. В `worker/wrangler.toml` укажите действительные `GITHUB_OWNER`, `GITHUB_REPO`, `GITHUB_BRANCH` и `ALLOWED_ORIGIN`. **`ALLOWED_ORIGIN` — только происхождение сайта, без пути** (например `https://andy-pal-hub.github.io`).
4. Выполните:

   ```bash
   npx wrangler login
   npx wrangler deploy
   npx wrangler secret put GH_TOKEN
   ```

   Последняя команда запросит токен, который будет сохранён как **Cloudflare Secret**, а не как файл в репозитории. После обновления секрета повторный деплой, как правило, не требуется.
5. Скопируйте HTTPS-адрес Worker из ответа Cloudflare и укажите в `config.js` в поле `endpoint`, дописав `/collect`:

   ```javascript
   window.PW_CONFIG = Object.freeze({
     endpoint: "https://your-worker.your-subdomain.workers.dev/collect",
     repo: "Andy-pal-hub/pw-class-test"
   });
   ```

6. Сохраните `config.js` в GitHub и обновите сайт. Для проверки откройте `https://адрес-worker/health` и убедитесь, что `configured` равно `true`. Это проверяет настройки, **но не запись**. Затем пройдите сайт, включив согласие на отправку обезличенных результатов, и убедитесь, что новая запись появилась в `data/runs.json`. Отправьте замечание к вопросу и проверьте `data/feedback.json`.

**Worker не отправляет PAT в браузер.** Он принимает только `POST /collect` с разрешённого Origin, валидирует тип/ID/размер данных и обновляет JSON в репозитории с повтором при конфликте записи. Ограничение Origin **не защищает от прямых запросов злоумышленника**: для открытого масштабного сайта потребуется Turnstile/защита от спама и более подходящая БД. Для малого ручного пилота это компромисс, не универсальный продакшен-бэкенд.

## Как собираются события

`runs.json`: запись **обновляется** по `session_id` (поэтому изменение оценок в том же прохождении не создаёт дубль). Сохраняются ID+ответы вопросов, дата завершения, статус (`sufficient`, `limit`, `ambiguous`, `conflict`), лучший класс и альтернативы, оценка результата. Данные отправляются **только с включённым чекбоксом согласия** либо при явном нажатии кнопки отправки финальной оценки.

`feedback.json`: запись **обновляется** по сочетанию `session_id + question_id`. Каждое замечание содержит ID вопроса, текущий вариант ответа, номер шага, текст вопроса и комментарий. Для отправки требуется нажать соответствующую кнопку в нижнем правом углу карточки. Так можно исправить отзыв, не плодя дубликаты.

В браузере используется локальная очередь с повторной отправкой после восстановления сети. Данные, отправленные без доступного Worker, **не появляются в GitHub автоматически, пока клиент не подключится и не повторит отправку**. В случае проблем можно выгрузить JSON вручную.

## Получение статистики

После загрузки или клонирования репозитория выполните:

```bash
python tools/analyze.py
```

Получите число завершений, распределение рекомендованных классов, оценки и отзывы по ID вопросов. Для надёжной аналитики и статистической калибровки понадобятся дополнительные проверки на реальных пользователях: описанные проценты совпадения — оценки матрицы, не вероятности.

## Известные ограничения

- Некоторые оценки классов и вопрос Q04-B требуют экспертной проверки.
- Вопросы E01–E06 из экспертной калибровки пока не подключены, чтобы не создавать невалидные веса только для некоторых классов.
- GitHub `data/*.json` публичны. При сборе персональных данных потребуется другая архитектура и политика обработки.
- HTML открывается локально, но для онлайн-отзывов и общей статистики нужен развёрнутый Worker.

## Пилот v0.5: проверка влияния дистанции

- **Q03: 1 → 1,3** для ответа о типе урона (вариант «неважно» по-прежнему 0).
- **Дистанция: 1 → 2**. Q02-A автоматически означает предпочтение дальнего боя и получает вес 2. Остальным после четырёх основных вопросов обязательно задаётся U06 о дистанции с весом 2. Нейтральное U06-D не начисляет баллы.
- Другие признаки и вопросы имеют вес 1. Это эксперимент, не статистически обученная калибровка.
- Исправлено Q04-C: учитывает 75% дамагера и 25% зависимости от PvE-экипировки.
- Исправлено излишнее перекрытие U16–U18 ответом Q02-D: отдельные уточнения о трансформации, сложности и комбинациях больше не исчезают.
- Величина 70–90% по-прежнему означает отношение среднего балла к 5, а не вероятность/уверенность.
- Учитываются все 17 классов; физический урон по Q03 не исключает классы без явного ответа об обязательности P02.
- Экспорт и статистика версии v0.5 помечены `0.5-weights-pilot` для сравнения пилотных данных с предыдущим вариантом.


## v0.6 — жёсткое ограничение дистанции (эксперимент)

- Вопрос **U06** задаётся всем игрокам, в том числе выбравшим Q02-A.
- Дополнительно доступны ответы **E — только ближний бой** (дальность 0–2 из 5) и **F — только дальний бой** (3–5 из 5).
- При E/F неподходящие классы полностью исключаются **до** расчёта рейтинга и списка альтернатив, независимо от веса остальных признаков. Фильтр не ослабляется автоматически.
- Ответы U06 A/B/C остаются **мягкими** (вес 2), D — нейтральный. E/F не прибавляют баллов соответствующим классам: это исключительно ограничения.
- Если Q02-A ранее обозначил дальний бой, оценка Q02-A при итоговом расчёте заменяется полноценным вопросом U06, чтобы не учитывать одну и ту же дистанцию дважды.
- Если совокупность жёстких условий не оставляет класса, тест честно выдаёт «Требования несовместимы» и предлагает вернуться и изменить ответ, не выдавая исключённый класс.
- В статистику/экспорт добавлены `distance_requirement` (`melee` / `ranged` / `null`) и `distance_threshold: 2`; версия `0.6-distance-hard`.
- Архетип, оформление и автономная работа сохранены; базовая v0.5 не изменялась.


### Совместимость приёмника v0.6

Клиент проверяет возможность `distance-hard-v1` через `/health`. Пока Cloudflare использует старый приёмник, новые события остаются в локальной очереди. После обновления приёмника очередь повторно отправляется при открытии страницы, восстановлении сети или следующей отправке. Это предотвращает потерю ответов E/F при раздельной публикации сайта и Worker.

Проверки: `node tools/test-quiz.mjs` (1 536 прохождений и очередь статистики), `node worker/test-worker.mjs` (приёмник и сохранение новых ответов).
